# cv

The source of truth for my CV, and a working example of how I use Claude Code
and agentic development: every application gets a CV tailored to that job
spec, generated by a skill, checked and edited by hand, then rendered to a
two-page PDF by a deterministic build.

## Why

A CV sent everywhere says the least to any one reader. The full record - every
role, with the work described in detail - is far more than two pages, and
which two pages it should become depends on the job. So the record and the CV
are kept separate: `roles/*.md` holds everything, one file per past role, and
a Claude Code skill selects and reframes from those files against a specific
job spec. Applying to a role costs minutes rather than an evening, and each
application leads with the evidence that spec actually asks for.

## How it works

```
roles/*.md          one file per past role - a superset of any single CV
qualifications.md   degrees, schooling, certifications
profile.md          direction, tooling, the summary's raw material
    │
    ▼               /generate-cv - read a job spec, select and reframe
cv.md               generated, then reviewed and edited by hand - gitignored
    │
    ▼               make - validate, then pandoc + weasyprint
dist/cv.pdf         the two-page PDF that gets attached
```

Three Claude Code skills drive it:

- **`/add-role`** captures a past role by interview - five waves of questions,
  pushing for hard numbers - and writes a structured file to `roles/`. Each
  file is a superset of what any single CV would show, carrying tailoring
  metadata alongside the facts: what leads for which kind of role, who did
  what, and which figures are confirmed.
- **`/assess-fit`** holds a job spec against the whole record before anything
  is written: which requirements are met with evidence, which are not, and a
  base-rate estimate of how far the application is likely to get. It writes
  nothing to disk.
- **`/generate-cv`** reads the spec, picks a register - senior developer,
  technical lead, founder, and so on - then selects and reframes from
  `roles/*.md` into `cv.md`.

The generated `cv.md` is then mine to review and edit - the skill drafts, it
does not send. When it reads right, `make` validates the structure and renders
it: Pandoc to HTML, WeasyPrint printing the PDF from that same HTML so one
stylesheet governs the whole chain, and the build fails unless the result is
exactly two pages.

The split is the point. Choosing what goes on a CV is a judgement call, so it
runs through a skill with a human check behind it. Turning that choice into a
document is not, so it runs through a Makefile. The guardrails are encoded
where they matter: a validator that refuses to render a malformed `cv.md`, a
page-count check that treats fitting as a writing problem rather than a
formatting one, and writing rules in `CLAUDE.md` that the skills obey -
nothing invented, no figure that isn't confirmed in a source file, and every
claim scoped to who actually did the work.

## Notes

`cv.md` is gitignored on purpose: it is written for one application and
rewritten for the next, so it is a working file rather than a record -
`roles/*.md` is what gets kept. Nothing here is published as a web page; the
CV goes to one reader at a time.

Everything in this repo is publishable. It is public by design and written for
the same reader who receives the CV. Contact details beyond an email address
are injected at render time from environment variables and are never
committed.

```
make          everything          make check   validate cv.md only
make pdf      dist/cv.pdf         make pages   assert the two-page limit
make html     dist/index.html     make dated   a dated copy to attach
                                  make setup   create .venv, check tooling
```

First run needs `pandoc` on `PATH` and `make setup` for the
[WeasyPrint](https://weasyprint.org) venv. The fonts are vendored, so a build
touches the network at no point and renders the same on any machine.
